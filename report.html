01

Executive summary

The Alumni Platform is a server-rendered CRUD application for maintaining a college alumni directory, seeded with 12 sample graduates spanning batches 2015–2024 across four departments. It began as a minimal login-and-directory app and grew, over the course of development, into a small campus network: alumni can self-manage their own profile, RSVP to reunions, post job referrals, and search each other out as mentors — while a single admin account moderates new signups, the master directory, and events.

Every screen is rendered server-side through Thymeleaf; there is no separate frontend build. Authorization is enforced twice over — once at the URL level in SecurityConfig, and again inside individual controller methods wherever a rule is more specific than "any authenticated user" or "admins only" (for instance, you may edit this record only if it's yours).

System architecture

3.1

Layered overview

A conventional Spring MVC layering, with Spring Security's filter chain sitting in front of every request and method-level @PreAuthorize checks living inside the controller layer alongside manual ownership checks that URL rules alone can't express.

Fig. 1 — Request flow through the application. Controllers depend only on services; services depend only on repositories; nothing skips a layer.

Data model

4.1

Entity relationships

There are no foreign keys between users and alumni — a login account and a directory record are linked only by matching email address at the application layer. This was a deliberate simplification: AlumniController.profile() looks up an alumni row by the signed-in user's email on every visit to "My Profile" rather than storing a hard reference.

Fig. 2 — The four persistent entities. Only Event.attendees uses a real join table (@ElementCollection); every other cross-entity link is a plain email string.

05

Security & access control

5.1

Authentication model

  • Session-based form login — no JWT. SecurityConfig is built entirely with the Spring Security 7 lambda DSL (authorizeHttpRequests, formLogin, logout); no deprecated WebSecurityConfigurerAdapter or chained .and() calls.
  • Passwords are hashed with BCryptPasswordEncoder before every save; the raw value never touches the database.
  • CSRF protection is on by default. Because every form uses Thymeleaf's th:action, Spring's CsrfRequestDataValueProcessor silently injects the hidden _csrf token — no template had to reference it explicitly.
  • Registration approval gate: a new User is created with approved = false. UserService.loadUserByUsername() maps that straight onto Spring Security's UserDetails.disabled flag, so an unapproved account authenticates correctly but is rejected with a DisabledException. A custom AuthenticationFailureHandler tells that apart from a wrong password, redirecting to /login?disabled instead of the generic /login?error.

06

Feature catalog

Directory

Combined search & pagination

Batch, department, and skill filters combine in a single JPQL query (AlumniRepository.search), 10 results per page, sorted by name.

Self-service

My Profile

An approved alumni account can create exactly one directory record and edit only that record — the server silently overwrites any submitted email back to the signer's own, so identity can't be spoofed through the form.

Self-service

Profile photo

Uploaded via multipart form, stored as raw bytes in Postgres, streamed back through a dedicated image/* endpoint — no filesystem or object storage dependency.

Directory

Find a mentor

Free-text, case-insensitive search across the comma-separated skills field.

Community

Events & RSVP

Admin-created reunions; any alumni can RSVP or cancel. Attendance is a plain set of email strings, rendered live on the event page.

Community

Job & referral board

Any approved alumni can post an opening; only the original poster (or an admin) can take it down — the delete button itself is hidden from everyone else, not just blocked server-side.

Admin

Registration approval queue

New signups sit disabled until an admin approves them from /admin/pending-users, closing the open-self-registration gap the app started with.

Admin

Dashboard & CSV export

Live counts (alumni, users, departments) plus a Chart.js bar chart of alumni-per-department; one-click CSV export of the full directory.

08

Engineering field notes

A record of the real problems hit during development — kept because each one changed something in the final codebase, not as a post-mortem gloss.

01 build · lombok

Lombok silently stopped generating code on JDK 25

Compiling with Maven produced cannot find symbol: method builder() and getX()/setX() errors across every entity, with no annotation-processor warning at all — the classic symptom of a processor that never ran.

[ERROR] DataInitializer.java: cannot find symbol symbol: method builder() location: class User
root cause  maven-compiler-plugin's default in-process compilation adds -XDuseUnsharedTable=true, which breaks Lombok's javac AST patching without raising an error.
fix  forced <fork>true</fork> and pinned Lombok explicitly via <annotationProcessorPaths> in pom.xml.
02 environment · java_home

System JAVA_HOME pointed at a path that didn't exist

JAVA_HOME was set to ...\Java\jdk-25\bin; the real install lived at ...\Java\jdk-25.0.3 (no bin suffix). Every mvnw invocation failed before touching the project.

fix  overrode the variable per-session for build commands rather than touching the machine's system configuration.
03 runtime · postgresql

Combined search broke the entire alumni list, not just skill filtering

After adding the batch + department + skill search, every visit to /alumni — including the default page right after login — returned a 500.

ERROR: function lower(bytea) does not exist

The JPQL used LOWER(CONCAT('%', :skill, '%')). With no skill filter applied, :skill bound as null; PostgreSQL couldn't infer that parameter's type at prepare-time and resolved it against the newly-added photo bytea column instead.

fix  build the lower-cased %pattern% string in Java and bind it as a concrete, typed String — no CONCAT/LOWER ever touches an ambiguous null parameter.
04 database · migration

Adding a NOT NULL column to a live table

User.approved was added as @Column(nullable = false) against a database that already held seeded admin/user rows. Hibernate's ddl-auto=update emits a plain ALTER TABLE ... ADD COLUMN ... NOT NULL with no default, which Postgres rejects outright against existing rows.

fix  manually backfilled via psql (ADD COLUMN approved boolean NOT NULL DEFAULT true) before the next application restart.
05 tooling · ide

Two unrelated projects, one folder

The working directory also contained a pre-existing, unrelated starter (backend/ + frontend/, package com.technoboost). Opening the wrong root in IntelliJ landed on BackendApplication.java instead of AlumniPlatformApplication.java, with no error to signal the mix-up.

fix  confirmed the correct project via IntelliJ's Search Everywhere rather than trusting the visible file tree.
09

Running the project

  1. Install JDK 25 and have PostgreSQL running locally with a database named alumni_db.
  2. Set the real database credentials in src/main/resources/application.properties (spring.datasource.username / password).
  3. From the project root: ./mvnw spring-boot:run — or open the folder in IntelliJ, set the Project SDK to JDK 25, enable annotation processing (Settings → Build, Execution, Deployment → Compiler → Annotation Processors) with the Lombok plugin installed, and run AlumniPlatformApplication.
  4. On first boot, DataInitializer seeds two accounts, 12 alumni, 2 events, and 2 job postings — but only if those tables are still empty.
  5. Visit http://localhost:8080/login.
Default logins — admin: admin@alumni.com / admin123. Alumni: user@alumni.com / user123. Both are pre-approved by the seed data.
